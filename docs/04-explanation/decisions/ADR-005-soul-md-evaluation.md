# ADR-005：不采用 `dsh-soul-md`，但借鉴其记忆字段设计

- **状态**：已接受
- **日期**：2026-11-01
- **背景**：发现 `dsh-soul-md@0.10.5`（人设卡 + 长期记忆插件）与 `dsh-qq-whale` 的人格/记忆层高度重叠，需判断是否替换

## 一、soul-md 实际提供了什么（读包内 README + 源码所得）

| 能力 | 字段 / 工具 | 状态 |
|---|---|---|
| 人设卡创建与编辑 | 插件页创建、填名称与 Markdown 内容 | ✅ 现成，比我们做得完整 |
| 人设可被不同工作区/会话选用 | 新会话页或聊天标题栏切换 | ✅ |
| 分层记忆 | `memory.layered`：`core.md`（常驻）+ `topics/*.md`（按需） | ✅ 与我们设计的分层一致 |
| 记忆工具 | `memory_read` / `memory_append` / `memory_rewrite` / `memory_search` | ✅ 现成 |
| 关键词召回 | `memory.recall = keyword`，从第二条用户消息起提示相关主题 | ✅ |
| 索引模式 | `memory.indexMode = all \| recall`（避免每轮注入完整索引） | ✅ |
| 压缩后补偿 | `memory.compactionRecall`：压缩/裁剪后提示近期主题摘要 | ✅ 正是我们担心的"压缩丢记忆" |
| 注入预算 | `memory.injectMaxChars = 8000` | ✅ |
| 跳过子代理 | `skipSubagents` | ✅ |
| 人设读写工具 | `soul_read` / `soul_update` | ✅ |

## 二、决定性差异：它没有"分区键"

README 明确写着：

> 记忆默认位于 **`$DSH_HOME/soul-md/memory/`**

这是一个**单一的全局目录**。它支持"为不同工作区或会话选择**人设卡**"，但记忆本身没有按群/会话分片的机制。
它的记忆工具签名是 `memory_read(topic)`——**只有 topic，没有 scope**。

而本方案的核心不变量是：

- **群级记忆分片**：每个群的梗与共同经历不串台（分区键 `group_id`）；
- **跨群人物记忆**：以 QQ 号为键跨群认识同一个人（分区键 `user_id`）；
- **出口检查**：回复发出前扫描，防止在 B 群说出 A 群的事。

这三条 soul-md 一条都不提供。更关键的是——**它的分区由 Agent 决定**（模型传什么 topic 就写哪），
而本方案的立场是：**分区必须由代码根据当前会话强制，不能交给模型**。模型决定的分区 = 随时可能串台。

## 三、决策

**不采用 soul-md 作为记忆引擎**，人格与记忆层继续由 `dsh-qq-whale` 自研。

理由不是"我们写得更好"，而是**分区键是安全边界，不是功能选项**。
换一个没有作用域的引擎，等于把群级隔离从"代码强制"降级成"模型自觉"。

**但它验证了我们方向正确，且有几处直接抄**：

| 抄什么 | 用在哪 |
|---|---|
| `core.md` + `topics/*.md` + 索引 | 我们的记忆目录结构（已一致） |
| 分层开关 + 关键词召回 + `indexMode` | 召回策略：默认不每轮注入完整索引 |
| `memory.compactionRecall` | 压缩后补偿——我们设计里有但没实现，应补 |
| `memory.injectMaxChars` 预算 | 记忆注入必须有字符预算 |
| `skipSubagents` | 子代理不注入人格与记忆 |

## 四、什么时候可以重新考虑

- soul-md 的 `memory_*` 工具**支持 scope / 分区键参数**时；
- 或我们给它提 PR 加上作用域，且被接受时；
- 或将来只做私聊机器人（不存在跨群串台风险）时。

## 五、代价

- 我们继续维护自己的记忆层（写入闸门、召回、出口检查都要自己写）；
- 人设卡的编辑体验暂时不如 soul-md（它没有我们的结构化字段，我们有但表单待补）。
