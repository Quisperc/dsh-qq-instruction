# QQBot 架构说明（写给完全不懂的人）

> 这份文档假设你**没听说过** DSH、Cordis、OneBot，也不写代码。
> 读完之后你应该能回答三个问题：QQ 里的一句话，是怎么变成机器人的回复的；出问题该去看哪个文件；哪些说法是常见的误解。
>
> 本文只讲**这台机器上**的实际部署（版本号、路径都是真的）。换一台机器，路径可能变，结构不变。

---

## 0. 先看一张图

记住一句话：**消息进来是一条路，回复出去是同一条路倒着走。** 中间任何一个环节断了，表现都是「机器人不说话」。

## 1. 一句话总览

QQ 客户端 → **NapCat**（协议翻译 + 门卫）→ **dsh-qq-bot**（接线员，负责收发与会话）→ **DSH**（大脑/宿主）→ **agent**（被赋予人设和能力的执行者）→ 回复沿原路返回。

再通俗一点：

- **NapCat 是翻译官**：QQ 说的话只有 QQ 自己懂，NapCat 翻译成一种叫 OneBot 11 的通用格式。
- **dsh-qq-bot 是接线员**：决定谁的电话该接、接到哪个分机上。
- **DSH 是公司**：提供办公室（进程）、人事档案（会话）、公共设施（工具、模型接口）。
- **agent 是员工**：临时被分配了岗位说明（人设）和工作权限（工具），干完这一单就歇着。
- **模型 provider 是外部顾问**：真正「想出这句话」的是它，不在你机器上。

## 2. 六个角色：谁写的、装在哪、坏了什么样

| 角色 | 谁开发的 | 装在哪 / 在哪运行 | 它坏了会怎样 |
|---|---|---|---|
| **QQ 客户端** | 腾讯 | 你自己的手机/电脑 | 消息发不出去；与机器人无关 |
| **NapCat** | 第三方开源（社区） | **机器外部**，地址 `wss://qapi.civer.cn`，登录的 Bot QQ 是 `2174357664` | 机器人完全不说话；`qqbot status` 会显示未连接 |
| **dsh-qq-bot** | 第三方社区插件（作者 sputnikzaychik），版本 **v0.12.8** | `/data/dsh/profiles/web/node_modules/@sputnikzaychik/dsh-qq-bot` | 连上了但永远不回；设置页的「QQ 机器人」打不开 |
| **DSH 本体** | DeepSeek 官方，版本 **0.2.2-rc.3** | `/usr/local/lib/node_modules/@deepseek-ai/dsh` | 整个网页打不开（不是 QQ 的问题，是宿主没了） |
| **dsh-qq-whale** | 本仓库自己写的，版本 **v0.14.0** | 源码 `/data/dsh/home/QQBotV2/dsh-qq-instruction/packages/dsh-qq-whale`，通过软链接进 profile | 新会话建不起来 → 机器人对每条消息都回「内部错误」 |
| **模型 provider** | leaflow（第三方云服务） | 不在这台机器上；模型 `deepseek-v4.1-flash-1017` | 有「正在输入」但没回复；日志里出现模型调用失败 |

两个补充说明：

- **插件（plugin）** 是什么？可以理解成「给 DSH 装的一块功能电路板」。装上不等于通电，还要被写进配置清单（见第 4 节误解 2）。
- **谁是「第三方」**？`dsh-qq-bot` 是社区作者写的、通过 npm 下载的；`dsh-qq-whale` 是我们自己仓库里的，改它要改源码。

## 3. 一条消息的完整旅程

假设你在群里 @ 了机器人，说「在吗」。

### 3.1 正常流程（10 步）

| 步 | 发生了什么 | 通俗解释 |
|---|---|---|
| ① | 你的 QQ 把消息发给腾讯服务器 | 正常聊天 |
| ② | NapCat 收到后，翻译成 OneBot 11 格式的 JSON | 翻译官把外语翻成普通话 |
| ③ | NapCat 通过 WebSocket 把 JSON 推给本机 | 电话打进来了 |
| ④ | DSH 里的 **adapter 子进程**收到这串 JSON | 前台接起电话 |
| ⑤ | **dsh-qq-bot** 判断准入：这个群在白名单吗？是 @ 吗？私聊允许吗？ | 接线员核对：这通电话要不要转 |
| ⑥ | 找到「这个聊天」对应的 DSH 会话；没有就新建一条 | 找到这位客户的历史档案，没有就新建一份 |
| ⑦ | 组装 agent：按 `preset` 决定挂哪些插件，把 `persona.text`（人设卡）拼进**第一轮** | 给员工发岗位说明和工作权限 |
| ⑧ | agent 把上下文发给模型 provider，模型决定说什么、要不要调工具 | 员工请示外部顾问 |
| ⑨ | 需要调工具时（查历史、搜网页、画图…）由 agent 调用，结果回填后再问模型 | 员工去查资料再汇报 |
| ⑩ | 最终文本交给 adapter，沿原路发回 NapCat，NapCat 发到 QQ | 回复送出门 |

### 3.2 每一步失败会有什么表现

| 失败在哪 | 你会看到什么 | 先查哪里 |
|---|---|---|
| ②/③ NapCat 断了 | 完全不回，像死了一样 | `qqbot` 工具的 status，看 `connected` |
| ④ adapter 崩了 | 同样完全不回；status 里 adapter 的 pid 会变或消失 | status 里的 `adapter.pid` / `restarts` |
| ⑤ 准入拦下 | 只有部分群不回（比如没 @ 就不理，这是设计） | `profiles/web/cordis.patch.yml` 里 `group` / `private` 段 |
| ⑥/⑦ 建会话失败 | 回一句「内部错误」「无法创建对话会话」 | 插件 `dsh-qq-whale` 是否在、`agentPresetCustom` 填的 id 是否存在 |
| ⑧ 模型调用失败 | 有「正在输入」，最后没消息 | 日志里找模型报错；确认 provider 凭据 |
| ⑨ 工具报错 | 会说话，但内容变成「工具被拒绝」「找不到」 | 会话日志里 `tool` 相关事件 |
| ⑩ 发送失败 | agent 认为发了，你收不到 | status 里的 `errors` / `chunksSent` |

## 4. 两个最容易混淆的概念

### 4.1 `preset` 不是沙箱，它只是一张「能力清单」

**preset** 可以想成一份**排班表**：告诉 DSH「这个会话要把哪些插件挂上来」。

关键是：**排班表决定不了谁能进门。** 在这台机器上，除了排班表里挂的那些插件，DSH 还有一大批「全局注册」的工具（比如执行命令、开终端、派子任务）。这些工具对会话里的人是**默认看得见**的，除非有人显式把它们挡掉。

所以：

| 说法 | 对不对 |
|---|---|
| 「用了受限 preset，它就碰不到危险工具了」 | ❌ 错。实测会话里曾经能看见 82 个工具 |
| 「真要限制必须显式调用 `tools.guard()`（执行期拦）或 `tools.restrict()`（连看都看不见）」 | ✅ 对。这两件事都由 `dsh-qq-whale` 的 `agent-guard.js` 做，与 preset 无关 |

本仓库的做法分两层：`preset-qq` 只决定挂哪些插件行；真正的收窄由 `dsh-qq-whale` 的 `lib/agent-guard.js` 完成——agent 创建时装 `tools.guard()`（执行期拦截），首个 `agent/pre-step` 再用 `tools.restrict()` 把白名单外的工具从可见列表里摘掉（23 项白名单，改哪个由设置页的 `allowTools` 决定）。

### 4.2 人设（人格）有两条通道，别以为写一处就够了

| 通道 | 写在哪 | 什么时候进模型 | 效果 |
|---|---|---|---|
| **风格锚点** | `preset-qq` 里的 `persona.prefix` | **每一轮**都在系统提示里 | 一直在提醒「你不是助手，是群友」 |
| **人设卡** | `dsh-qq-bot` 的 `persona.text`（约 4.5k 字） | **只在会话第一轮**，拼在用户消息末尾 | 一次讲清「你是谁、性格、雷区、说话方式」 |

两条通道不冲突，但**会各说一遍「你是谁」**。也正因人设卡只发一次，它不占每轮的 token，**不要为了省 token 去砍它**。

## 6. 进程边界：谁在谁里面

```
宿主机 / 容器
├── 1Panel 入口脚本
│    ├── dsh web（主进程，:3080）        ← DSH 本体、插件、会话都在这个进程里
│    │    └── adapter 子进程            ← qq-bot 派出来专门连 NapCat 的
│    └── caddy（反向代理，对外提供 HTTPS）
└── NapCat（在别的机器/服务上，不在这里）
```

两点实用含义：

1. **adapter 是子进程**，所以它挂了主进程还在，可以在设置页重连；但**主进程挂了**（比如容器重启）就全停。
2. **改配置后不一定立即生效**：插件可以热重载，但涉及「会话怎么建」的改动，往往要等**新会话**才生效。

## 7. 常见误解清单

1. **「preset 就等于权限限制」** —— 错。preset 只决定挂哪些插件；真正拦工具要靠 `tools.guard()` / `tools.restrict()`（在 `dsh-qq-whale` 的 `agent-guard.js` 里，与 preset 无关）。
2. **「装进 dependencies 就等于启用了」** —— 错。装包只让它出现在磁盘上；还要在 `dsh.profile.bundles` 里登记、并在配置里挂载，才算真正跑起来。
3. **「改完配置一定立即生效」** —— 错。配置改完可能只对**新会话**生效；已经在聊的那条会话，还是旧的能力与人设。
4. **「会话可以随便换 preset」** —— 错。preset 在会话创建时就定了；换 preset 要新建会话，硬改配置却不清会话，可能出现「配了 A 却在跑 B」。
5. **「群里不回复就是坏了」** —— 未必。群聊默认要求 **@** 才理；没 @ 它就该沉默，这是准入策略，不是故障。
6. **「人格卡越长越浪费钱」** —— 恰恰相反。人设卡只在第一轮发一次，是「一次性开销」；每轮都发送的是短的那个风格锚点。
7. **「重启能解决一切」** —— 有时能（比如进程状态坏了），但也会清空临时文件（`/tmp` 下的东西会没）。重启前把要紧的文件放到 `/data/dsh/home` 下面。

## 8. 出问题时的排查顺序（照着走）

1. **先看连接**：调用 `qqbot` 工具查 status，`connected` 是 `true` 吗？adapter 的 pid 在吗？
2. **再看准入**：这条消息来自哪个群/哪个私聊？在 `allow` 名单里吗？群聊是不是忘了 @？
3. **再看会话**：`/data/dsh/sessions/--data-dsh-home-Documents-deepseek-harness-QQ_msg--/` 下有没有新目录？有目录但没回合，说明卡在建 agent。
4. **再看配置**：`/data/dsh/profiles/web/cordis.patch.yml` 里 `agentPresetCustom` 填的 id，在组合里真的存在吗？
5. **最后看插件**：`dsh-qq-whale` 在不在、版本对不对、依赖有没有被误删。它的职责只有一个：注册 `preset-qq`。

一个小提醒：**别在运行中的会话里杀掉主进程**。容器入口脚本会跟着退出，整个容器就停了——要重启请在面板里操作。
